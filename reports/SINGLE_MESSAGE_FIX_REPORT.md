# SINGLE MESSAGE FIX REPORT

## Какая была проблема

- После /start бот показывал экран выбора сегмента.
- После выбора сегмента появлялось отдельное сообщение «Вы выбрали: …».
- Затем ещё одним новым сообщением приходил первый шаг воронки.
- Scheduler отправлял шаги 2+ как новые сообщения (send_message), не редактируя основное.
- Кнопки дублировались («Назад» и «Сменить направление» с одним действием).
- Нарушался принцип Single-Message UI: один экран — одно сообщение.

## Что изменено в архитектуре

- В модель User добавлены поля для хранения основного экрана: `chat_id`, `ui_message_id`, `updated_at`.
- Введён централизованный сервис `ui_service`: `send_or_update_ui_message`, `safe_edit_or_resend`, `save_user_ui_message`, `get_user_ui_message`. Вся логика «отправить или отредактировать» и fallback при ошибках Telegram сосредоточена в нём.
- Scheduler при отправке шага воронки получает у пользователя `chat_id` и `ui_message_id`, пытается отредактировать это сообщение; при неудаче отправляет новое и обновляет контекст в БД.
- Обработчики /start, выбора сегмента, заявки и навигации работают через одно главное сообщение: создают его один раз и дальше только редактируют (или fallback — новое сообщение с обновлением id).

- `reports/SINGLE_MESSAGE_FIX_REPORT.md` — данный отчёт.

- `models/user.py` — добавлены chat_id, ui_message_id, updated_at.

- `services/scheduler_service.py` — send_scheduled_funnel_step переведён на редактирование основного сообщения пользователя с fallback.

- `handlers/lead.py` — после отправки заявки обновляется основное UI-сообщение (подтверждение) через send_or_update_ui_message.

## Как теперь работает /start

- Получение/создание пользователя, загрузка активных сегментов.
- Отправка одного сообщения со стартовым текстом и клавиатурой сегментов.
- Сохранение в user: chat_id и message_id этого сообщения (save_user_ui_message).
- Это сообщение считается главным экраном; все последующие экраны по возможности редактируют его.

## Как теперь работает выбор сегмента

- Пользователь нажимает сегмент.
- Сохраняется segment_id, отменяются старые job’ы воронки.
- То же сообщение (экран выбора) редактируется в первый шаг воронки: текст «Направление: {segment.name}» + текст шага 1, клавиатура шага (заявка, сменить направление).
- В user сохраняется контекст этого же сообщения (chat_id, message_id).
- Шаги 2+ планируются в scheduler; при срабатывании scheduler редактирует это же сообщение.

## Как теперь работают шаги scheduler

- Job получает telegram_id и step_id.
- По telegram_id находится user, из user берутся chat_id и ui_message_id.
- Вызывается safe_edit_or_resend: попытка edit_message_text.
- При успехе — логируем «Scheduled funnel step edit success».
- При неудаче (ошибка Telegram) — отправляется новое сообщение, в user сохраняется новый ui_message_id; логируем fallback.
- Дальнейшие шаги и действия используют уже обновлённый контекст.

## Как теперь работает смена направления

- Пользователь нажимает «Сменить направление» (nav:segments).
- Обработчик редактирует то же сообщение (edit_text) на экран выбора сегментов.
- Новое сообщение не создаётся; chat_id и message_id не меняются.

## Как теперь работает заявка

- «Оставить заявку» переводит в FSM, текущее сообщение редактируется в приглашение ввести текст (допустимое новое сообщение — ввод пользователя).
- После отправки текста заявки лид сохраняется, админу уходит уведомление.
- Основное UI-сообщение (то, что показывало приглашение) обновляется через send_or_update_ui_message на «Заявка отправлена» с клавиатурой шага. Отдельное новое сообщение с подтверждением не отправляется.

## Результат проверки

- /start: одно сообщение со стартовым экраном, ui_message_id сохраняется.
- Выбор сегмента: то же сообщение заменяется на первый шаг воронки, второго сообщения нет.
- Scheduler: обновляет то же сообщение (или fallback — одно новое с обновлением id), чат не засоряется.
- Смена направления: edit того же сообщения на выбор сегментов.
- Заявка: после ввода текста главное сообщение меняется на подтверждение.
